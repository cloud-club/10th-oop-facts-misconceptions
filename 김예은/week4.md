# Week 4. 역할, 책임, 협력

## 1. 기억에 남은 내용

4장에서 가장 기억에 남은 건 객체의 모양을 결정하는 것은 객체가 참여하는 협력이라는 내용입니다.

3장에서는 행동이 타입을 결정한다고 했는데, 4장은 그 행동이 어디서 오는지를 알려 줍니다.
어떤 협력에 참여하는지가 객체의 행동을 정하고, 그 행동이 다시 상태를 정한다는 점이 인상 깊었습니다.

## 2. 4장 정리

```text
협력: 요청과 응답이 이어지며 함께 문제를 해결한다
  → 책임: 요청을 받은 객체가 알아야 하는 것과 해야 하는 것
    → 역할: 책임의 집합. 같은 메시지를 이해하는 객체로 대체할 수 있다
      → 협력이 객체의 모양을 결정한다
```

### 문맥이 행동을 결정한다

장은 최후통첩 게임으로 시작합니다.
사람이 이기적이고 합리적이라면 최소 금액만 제안하고, 아무리 적어도 받아들여야 합니다.
하지만 실제로는 40% 이상을 제안한 사람이 가장 많았고, 적은 금액을 제안받은 사람은 대부분 거절했습니다.

사람의 행동을 정하는 건 타고난 특성이 아니라 다른 사람과의 협력이라는 문맥입니다. 객체도 마찬가지입니다.

### 협력

하트 잭의 재판은 왕, 하얀 토끼, 모자 장수가 요청하고 응답하면서 진행됩니다.

```text
1. 누군가 왕에게 "재판하라"
2. 왕이 하얀 토끼에게 "목격자를 불러오라"
3. 하얀 토끼가 모자 장수에게 "증인석에 입장하라"
4. 왕이 모자 장수에게 "증언하라"
```

혼자 해결하기 어려운 문제를 요청과 응답의 연쇄로 함께 해결하는 것이 협력입니다.

### 책임

요청을 받은 객체가 대답하거나 행동해야 할 의무를 책임이라고 합니다.
책임은 크게 두 가지로 나뉩니다.

- **하는 것 (doing)**: 왕이 하얀 토끼와 모자 장수에게 차례로 요청하며 재판을 이끈다
- **아는 것 (knowing)**: 하얀 토끼가 목격자가 모자 장수라는 걸 안다

책임은 객체가 외부에 제공하는 정보와 서비스라서, 객체의 공용 인터페이스가 됩니다.

객체는 메시지를 받았을 때만 책임을 수행하고, 메시지는 다른 객체에 접근하는 유일한 방법입니다.
책임은 메시지보다 큰 단위라서, 책임 하나가 여러 메시지로 나뉘기도 합니다.

### 역할

재판은 증인만 바꿔 가며 세 번 반복됩니다. 마지막에는 판사도 왕에서 여왕으로 바뀝니다.

| 협력 | 판사 | 증인 |
| --- | --- | --- |
| 첫 번째 | 왕 | 모자 장수 |
| 두 번째 | 왕 | 요리사 |
| 세 번째 | 여왕 | 앨리스 |

등장인물만 다를 뿐 과정은 완전히 같습니다.
그래서 판사와 증인이라는 역할로 보면 세 협력을 하나로 묶을 수 있습니다.

역할은 "이 자리는 이 역할을 할 수 있는 누구라도 대신할 수 있다"는 표식입니다.
덕분에 설계가 단순해지고, 유연해지고, 재사용하기 좋아집니다.

### 대체 가능성

증인 역할을 하려면 "증인석에 입장하라"와 "증언하라"를 이해할 수 있어야 합니다.
즉, 역할이 수행하는 책임을 똑같이 수행할 수 있어야 합니다.

대신 객체는 역할보다 더 많은 책임을 가질 수 있습니다.
왕은 나라를 돌보고, 모자 장수는 모자를 팔고, 앨리스는 이야기의 주인공입니다.

그래서 역할은 일반화, 객체의 타입은 특수화가 됩니다. 3장의 슈퍼타입과 서브타입 관계와 같습니다.

### 협력이 객체의 모양을 결정한다

왕을 설계할 때 왕관과 수염부터 떠올리기 쉽지만, 앨리스 이야기에서 왕이 중요한 이유는 판사 역할로 재판에 참여하기 때문입니다.
객체는 데이터를 담으려고 있는 게 아니라 협력에 참여하려고 존재합니다.

그래서 설계는 다음 순서로 해야 합니다.

```text
협력 → 책임(행동) → 데이터 → 클래스
```

### 설계 기법

| 기법 | 한 줄 요약 |
| --- | --- |
| 책임 주도 설계 | 시스템의 책임을 작게 나누고, 적절한 객체에게 할당하며 협력을 만든다 |
| 디자인 패턴 | 전문가들이 이미 찾아 둔 역할, 책임, 협력의 모음. 책임 주도 설계의 지름길이다 |
| 테스트 주도 개발 | 이름과 달리 테스트가 아니라 설계를 위한 기법이다 |

## 3. 같이 이야기해 보고 싶은 주제

- 책은 TDD가 테스트가 아니라 설계를 위한 기법이라고 말합니다. 테스트를 먼저 작성하면서 설계가 바뀐 경험이 있나요?
