# Week 3. 타입과 추상화

> 읽은 범위: 3장 「타입과 추상화」 (p.72~105)

## 1. 추상화 — 복잡한 것을 어떻게 단순하게 바라볼까?

3장에서는 **추상화**를 복잡한 대상을 이해하기 위해 목적에 필요한 특징을 남기고 불필요한 세부 사항을 생략하는 과정으로 설명한다.

책에 등장하는 지하철 노선도가 좋은 예시다. 승객에게 중요한 것은 역의 실제 위치나 거리보다 어떤 노선이 연결되고 어디에서 환승해야 하는가이다. 따라서 실제 지형을 모두 표현하지 않아도 이용 목적에는 더 적합한 지도가 될 수 있다.

추상화는 크게 두 방향으로 이해했다.

- **공통점으로 묶기:** 서로 다른 객체에서 공통적인 특징을 찾아 하나의 개념으로 분류한다.
- **불필요한 세부 사항 생략하기:** 목적과 관련 없는 차이는 감추고 중요한 부분에 집중한다.

여기서 인상적인 점은 **추상화가 단순히 정보를 적게 만드는 일이 아니라, 무엇을 남길지 선택하는 일**이라는 것이다. 같은 대상도 어떤 문제를 해결하려는지에 따라 다른 방식으로 추상화할 수 있다.

## 2. 개념과 타입 — 무엇을 기준으로 같은 종류라고 할까?

앨리스가 정원사, 병사, 여왕 등을 각각의 세부적인 차이보다 '트럼프'라는 공통된 개념으로 이해하는 장면은 분류를 통한 추상화의 예시다.

책에서 설명하는 개념의 세 가지 관점은 다음과 같다.

| 구분 | 의미 |
| --- | --- |
| 심볼(Symbol) | 개념에 붙인 이름 |
| 내연(Intension) | 개념을 정의하는 특징 |
| 외연(Extension) | 해당 개념에 속하는 객체들의 집합 |

이러한 개념을 소프트웨어 객체에 적용한 것이 **타입**이라고 이해했다. 특히 책은 객체의 타입을 생각할 때 내부 데이터보다 **객체가 어떤 행동을 할 수 있는가**를 중요하게 다룬다.

이는 2장에서 읽었던 '상태보다 행동이 중요하다'는 설명과 연결된다. 객체의 상태가 다르더라도 협력에서 동일한 책임을 수행할 수 있다면 공통된 타입으로 바라볼 수 있다는 것이다.

또한 **타입과 클래스는 같은 개념이 아니다.** 타입은 객체를 분류하는 기준이고, 클래스는 타입을 코드로 구현하는 방법 중 하나다.

## 3. 일반화·특수화와 정적·동적 모델

### 일반화·특수화

여러 타입이 공통적으로 수행하는 행동을 묶으면 더 일반적인 **슈퍼타입**으로 표현할 수 있고, 그보다 특화된 행동을 가진 타입은 **서브타입**으로 생각할 수 있다.

여기서 단순히 속성이 비슷하다는 이유로 상속 관계를 만드는 것보다는, **행동의 공통점과 대체 가능성**을 기준으로 관계를 판단해야 한다는 점이 중요하다고 이해했다.

### 정적 모델과 동적 모델

객체는 시간이 지나며 상태가 변하지만, 타입은 그러한 변화에서 공통적인 특성을 추려 상대적으로 안정적인 관점으로 표현한다.

- **동적 모델:** 객체가 시간에 따라 어떤 상태를 가지며 어떻게 행동하는지에 주목한다.
- **정적 모델:** 객체가 속한 타입과 그 타입의 속성·행동 등 구조에 주목한다.

두 관점은 서로 대체하는 것이 아니라, 같은 시스템을 다른 측면에서 이해하기 위해 함께 사용한다고 생각했다.

## 4. 실제 코드와 연결해 보기 — `todo-cli`

이전에 작성한 [todo-cli](https://github.com/cynkai/todo-cli) 프로젝트에는 할 일을 표현하는 `Task` 모델이 있다. `Task`는 `id`, `title`, `completed`를 가지고 있고, 완료 처리는 별도의 `complete_task()` 함수에서 수행한다.

할 일을 완료하면 `completed` 값이 `False`에서 `True`인 결과가 만들어진다. 구현상으로는 불변 모델을 사용하므로 새로운 객체를 반환하지만, **도메인 관점에서는 같은 ID를 가진 할 일의 상태가 달라졌다고 볼 수 있다.**

이 사례를 3장에 연결하면 다음과 같은 질문을 해볼 수 있다.

> 미완료 Task와 완료 Task는 상태가 다르다는 이유만으로 서로 다른 타입이어야 할까?

현재 요구사항에서는 둘 모두 '할 일'이라는 같은 개념으로 분류해도 무리가 없어 보인다. 상태가 바뀌었다는 사실만으로 타입까지 나눌 필요는 없기 때문이다.

다만 만약 완료 여부에 따라 **허용되는 행동이나 지켜야 할 규칙이 크게 달라진다면**, 하나의 타입과 상태 검사로 처리할지, 별도의 타입으로 구분할지 고민할 수 있을 것이다. 어떤 선택이 적절한지는 단순히 필드 값의 차이가 아니라 실제 요구사항과 행동의 차이에 달려 있다고 생각한다.

## 5. 토론하고 싶은 질문

1. **객체의 상태 변화와 타입을 분리해야 하는 상황은 어떻게 구분할 수 있을까?** 완료 여부처럼 상태만 달라지는 경우와, 상태에 따라 허용되는 행동이 달라지는 경우를 어떤 기준으로 설계하면 좋을까?
2. **추상화는 어디까지 하는 것이 적절할까?** 공통점을 묶어 구조를 단순하게 만들 수 있지만, 지나친 추상화가 오히려 코드를 이해하기 어렵게 만들 수도 있지 않을까?

## 6. 마무리

1·2장에서 객체의 **책임과 행동**을 생각했다면, 3장에서는 여러 객체의 공통점을 묶고 복잡한 상태 변화를 **타입으로 추상화하는 관점**을 배웠다고 정리할 수 있다.

이번 장에서 남은 질문은 **'서로 다른 객체들을 어떤 기준으로 같은 타입으로 바라볼 것인가?'**이다. 앞으로 코드를 읽거나 설계할 때 단순한 데이터 구조의 유사성보다 요구사항과 행동의 공통점을 먼저 살펴보고 싶다.
