테이블 한 칸에 담긴 다형성, trackable_type

Rails의 polymorphic association을 예로, “무엇이든 추적할 수 있는” action_trackings 테이블이 타입·추상화·다형성을 어떻게 다루는지 살펴봅니다.

1 · 문제

게시글도, 댓글도, 사용자도 추적하고 싶다

“누가 무엇을 했는가”를 기록하는 action_trackings 테이블을 만든다고 해 봅시다. 추적 대상이 Post 하나라면 post_id 컬럼이면 충분합니다. 그런데 댓글, 사용자, 주문까지 늘어나면 post_id, comment_id, user_id, order_id… 대부분이 비어 있는 컬럼이 계속 늘어납니다.

polymorphic association은 이 컬럼들을 두 칸으로 줄입니다. 어떤 종류인지(trackable_type)와 그중 어느 것인지(trackable_id)입니다.

2 · 데이터

행을 눌러 Rails가 대상을 찾아가는 과정을 보세요

action_trackings (예시 데이터)
idactiontrackable_typetrackable_id
① 문자열을 클래스로 바꾸고 id로 찾기
② 실행되는 SQL
③ 같은 메시지 tracking.trackable.summary의 응답

3 · 코드

Rails에서는 이렇게 선언합니다

db/migrate/…_create_action_trackings.rb
create_table :action_trackings do |t|
  t.string     :action
  t.references :trackable, polymorphic: true, null: false
  # → trackable_type (string), trackable_id (bigint)
  # → 두 컬럼을 묶은 복합 인덱스
  t.timestamps
end
app/models/action_tracking.rb
class ActionTracking < ApplicationRecord
  belongs_to :trackable, polymorphic: true
end
app/models/concerns/trackable.rb · 각 모델
module Trackable
  extend ActiveSupport::Concern
  included do
    has_many :action_trackings, as: :trackable
  end

  # 이 역할을 맡는 객체는 summary 메시지에 응답해야 한다
  def summary = raise NotImplementedError
end

class Post < ApplicationRecord
  include Trackable
  def summary = "게시글 「#{title}」"
end

class Comment < ApplicationRecord
  include Trackable
  def summary = "#{post.title}에 단 댓글"
end
사용하는 쪽
ActionTracking.recent.each do |tracking|
  # 대상이 Post인지 Comment인지 묻지 않는다
  puts "#{tracking.action}: #{tracking.trackable.summary}"
end

trackable_type에는 무엇이 들어가나요? Rails 기본값은 테이블명(posts)이 아니라 모델 클래스명("Post")입니다. STI를 쓰면 하위 클래스가 아닌 base class 이름이 저장됩니다. 클래스명이 DB에 문자열로 박히기 때문에, 모델 이름을 바꾸면 기존 데이터도 함께 마이그레이션해야 합니다.

4 · 책과 연결하기

3장의 개념이 어디에 대응되는가

타입 · 일반화트럼프Trackable정원사·병사·신하의 차이를 버리고 “트럼프”로 묶듯, Post·Comment·User의 차이를 버리고 “추적 가능한 것”으로 묶습니다.
인스턴스 · 외연하트 여왕, 정원사 2("Post", 12)각 행의 type + id 쌍이 그 타입에 속하는 구체적인 객체 하나를 가리킵니다.
다형성같은 메시지, 다른 응답trackable.summary송신자는 하나의 메시지를 보내고, 실제 수신자가 누구냐에 따라 다른 메서드가 실행됩니다.
객체를 분류하는 기준은 타입이며, 타입을 나누는 기준은 객체가 수행하는 행동이다.— 3장 「행동이 우선이다」의 요지

ActionTracking은 대상의 구체적인 클래스를 모릅니다. 아는 것은 “trackable이라는 역할을 하는 무언가”뿐입니다. 덕분에 새로운 모델에 include Trackable만 붙이면 ActionTracking 코드는 한 줄도 바꾸지 않고 추적 대상을 늘릴 수 있습니다.

5 · 트레이드오프

DB 관점에서는 대가가 있다

  • 장점추적 대상이 늘어나도 테이블 스키마와 ActionTracking 코드는 그대로입니다.
  • 장점“모든 활동 기록”처럼 여러 종류를 한 목록으로 다루기 쉽습니다.
  • 단점trackable_id에 외래 키 제약을 걸 수 없습니다. 원본이 지워져도 DB는 모르고, 고아 행이 생길 수 있습니다.
  • 단점대상 테이블이 행마다 달라 일반적인 JOIN이 어렵습니다. includes(:trackable)은 타입별로 쿼리를 나눠 preload하고, eager_load(JOIN 방식)는 쓸 수 없습니다.
  • 단점클래스명이 데이터에 저장되므로 코드의 이름 변경이 데이터 변경으로 이어집니다.
6 · 이야기해 볼 거리

스터디 질문

  1. 책은 “타입은 행동으로 나눈다”고 합니다. 그런데 trackable_type은 타입을 데이터(문자열)로 저장합니다. 이 둘은 충돌하는 걸까요, 각자 다른 층위의 이야기일까요?
  2. trackable_type을 보고 case 문으로 분기하는 코드와, trackable.summary를 호출하는 코드는 무엇이 다를까요? 어느 쪽이 다형성을 활용한 걸까요?
  3. 헤리 벡의 노선도처럼, ActionTracking 입장에서 “지워도 되는 세부 사항”은 무엇이고 “남겨야 하는 본질”은 무엇일까요?
  4. 외래 키 제약을 포기하는 대가를 감수할 만한 상황과 아닌 상황을 각자의 서비스 예시로 나눠 봅시다.
예시 데이터와 코드는 설명용으로 만든 것입니다. 기준: Rails 7 이상의 belongs_to … polymorphic: true.
