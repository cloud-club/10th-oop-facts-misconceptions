## 자율적인 책임

### 설계의 품질을 좌우하는 책임

- 객체지향 공동체를 구성하는 기본 단위는 '자율적'인 객체다.
- **자율성** : 자기 스스로의 원칙에 따라 어떤 일을 하거나 자신을 통제해서 절제하는 성질이나 특성
- **타율성** : 자율성의 반대말, 자신의 의지와 관계없이 정해진 규율이나 원칙에 따라서만 움직이는 성질

타인이 정한 규칙이나 명령에 따라 판단하고 행동하는 객체는 자율적인 객체라고 부르기 어렵다.

요청을 처리하기 위해 객체가 수행하는 행동 = 책임

적절한 책임이 자율적인 객체를 낳고, 자율적인 객체들이 모여 유연하고 단순한 협력을 낳는다. 
따라서, 협력에 참여하는 객체가 얼마나 자율적인지가 전체 애플리케이션의 품질을 결정한다.

### '어떻게'가 아니라 '무엇'을

- 자율적인 책임의 특징은 객체가 How 해야하는가 아닌 What을 해야 하는 가를 설명한다.

## 메시지와 메서드

### 메시지

- 메시지-전송 메커니즘은 객체가 다른 객체에 접근할 수 있는 유일한 방법이다.
- "증언하라" : 메시지 이름 (message name)
- argument를 통해 추가 정보를 제공할 수 있다.
	- ex) 언제 어디에서 목격한 것을 증언하라고 요청하면 "언제", "어디서" 라는 부가정보가 실린다.

- 메시지는 메시지 이름과 인자로 구성된다.
-> `증언하라(어제, 왕국)`

- 메시지전송은 수신자와 메시지의 조합
-> `모자장수, 증언하라(어제, 왕국)`

- 객체가 수실할 수 있는 메시지의 모양이 객체가 수행할 책임의 모양을 결정한다.

### 송신자와 수신자를 약하게 연결하는 메시지

- 송신자는 오직 메시지만 바라본다. 수신자의 정확한 타입을 모르더라도 상관없다. 단지 수신자가 메시지를 이해하고 처리해줄 것이라는 사실만 알아도 충분하다.
- 수신자는 메시지를 처리하기 위해 자율적으로 메서드를 선택할 수 있지만 메서드 자체는 송신자에게 노출시키지 않는다.

- 수신자와 송신자는 메시지라는 얇은 끈으로만 이어져 있다. 
- 메시지를 기반으로 한 두 객체 사이의 이 낮은 결합도가 바로 설계를 유연하고 확장 가능하며 재사용 가능하게 만드는 비결이다. 
- 따라서 설계의 품질을 높이기 위해서는 훌륭한 메시지를 선택해야 한다

class AClass
	def a_to_b
		b = BClass.new
		 
		if b.b_condition
			b.b_method
		end
	end
	
	def a_to_c
		c = CClass.new		
		c.c_method
	end
end 

class BClass
	def b_method
		return 1
	end
	
	def b_condition
		1 == 2
	end
end

class CClass
	def c_method
		return unless c_condition
		
		return 1
	end
	
	def c_condition
		1 == 2
	end
end


class DClass
	def d_1
		if condition_1
			action_1
		end
	end
	
	def d_2
		action_2
	end
	
	def action_1
		print '1'	
	end 
	
	def action_2
		if condition_1
			print '2'
		end
	end
	
	def condition_1
		true
	end
	
	def condition_2
		false
	end
end

# DClass: 쿠폰을 관리하는 클래스
class CouponService:

            self.print_discount()

    def is_coupon_available(self):
        return True

    def is_coupon_expired(self):
        return False

## 인터페이스와 구현의 분리

### 객체 관점에서 생각하는 방법

맷 와이스펠드 왈) 객체지향적인 사고 방식을 이해하기 위해서 중요한 세가지 원칙

- 좀더 추상적인 인터페이스
	- "증언하라" 에 대한 예시
	- 너무 구체적인 인터페이스보다는 추상적인 인터페이스를 설계하는 것이 좋다.
- 최소 인터페이스
	- 외부에서 사용할 필요가 없는 인터페이스는 최대한 노출하지 말자.
	- 협력이라는 문맥을 고려하지 않고 객체 자체에 초점을 맞추는 경우에는 사용되지 않는 불필요한 메시지가 인터페이스를 더럽히는 것을 방지할 수 없다.
	- **(생각)** 예를들어 Getter, Setter Method를 무작정 다 만드는 상황이 가장 큰 것 같다. 의미없게 생각한 Setter 때문에 데이터의 변경 흐름을 제어하지 못하는 케이스가 생긴다.
- 인터페이스와 구현 간에 차이가 있다는 점을 인식

### 구현

- 객체를 구성하지만 공용 인터페이스에 포함되지 않는 모든 것이 구현에 포함된다.
	- **상태를 어떻게 표현할 것인가.**
	- **메서드를 구성하는 코드 자체**

- 객체의 외부와 내부를 분리하라는 것 = 객체의 공용 인터페이스와 구현을 명확하게 분리하라

### 인터페이스와 구현의 분리 원칙

**(생각)** 왜인지 모르게 DI 가 생각나고, Strategy Pattern을 통한 로직 주입 과정이나 Template Method Pattern이 생각난다.

- **인터페이스와 구현의 분리 원칙이 중요한 이유 = 소프트웨어가 항상 변경되기 때문이다.**
	- 안전지대가 객체의 내부인 구현이고 위험지대가 객체의 외부인 공용 인터페이스이다.

## 책임의 자율성이 협력의 품질을 결정한다.

![[Pasted image 20261123210355.png]]


**책임이 얼마나 자율적인지가 전체적인 협력의 설계 품질을 결정하게 된다.**

1. 자율적인 책임은 협력을 단순하게 만든다.
	- "증언하라" vs "ooo를 기억하고 xxx 를 활용해서 증언하라"
2. 자율적인 책임은 모자 장수의 외부와 내부를 명확하게 분리한다.
	- 내부적으로 증언을 하는 책임에 대해서, 증언할 방식을 자율적으로 선택할 수 있다.
3. 책임이 자율적인 경우 책임을 수행하는 내부적인 방법을 변경하더라도 외부에 영향을 미치지 않는다.
	- 모자 장수가 증언하는 방법을 변경하더라도 왕에게 미치는 영향은 없다. 
	- **변경의 파급효과가 객체 내부로 캡슐화되기 떄문에 두 객체 간의 결합도가 낮아진다.**
4. 자율적인 책임은 협력의 대상을 다양하게 선택할 수 있는 유연성을 제공한다.
	- "증언하라" -> 말로 하든, 동영상을 보내든 유연하다.
5. 객체가 수행하는 책임들이 자율적일수록 객체의 역할을 이해하기 쉬워진다.
	- "증인석에 입장한다. 증언하다." 이라는 책임
	- "증인" 이라는 역할
	- **책임이 자율적일수록 객체의 응집도가 높은 상태로 유지하기가 쉬워진다.**


(생각) 핵심문장: **책임이 자율적일수록 적절하게 "추상화"되며, "응집도"가 높아지고, "결합도"가 낮아지며, "캡슐화"가 증진되고, "인터페이스와 구현이 명확히 분리"되며, 설계의 "유연성"과 "재사용성"이 향상된다.**

**객체지향의 강력함을 누리기 위한 출발점은 책임을 자율적으로 만드는 것이다.**
