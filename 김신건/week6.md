# 6주차 - 06. 객체 지도 

> 유일하게 변하지 않는 것은 모든 것이 변한다는 사실 뿐이다.

```
(생각) 
현재 사내에서 주소, 배송 관련 정보를 다루는 경우가 많다.

이사를 가지 않는 한, 우리가 사는 위치는 변하지 않는다.
근데, 그 위치를 표현하는 주소는 달라질 수 있다.

예를 들어, 도로명 주소로 주소를 표현하는 방법이 달라질 수도 있고, 주소 체계가 바뀔 수도 있다. 

시스템은 과연 이 변화를 담아낼 수 있는가? 
```


- 길을 직접 알려주는 방법이 기능적이고 해결 방법 지향적인 접근법이라면 지도를 이용하는 방법은 '구조적이고 문제지향적인 접근법'이다.

- 길을 묻는 방법은 현재의 마을에서 다른 마을로 이동하는 현재의 요구만을 만족시킬 수 있다. 이에 반해 지도는 현재의 목적뿐만 아니라 다양한 목적을 위해 재사용될 수 있다. -> 지도는 범용적이다.
	- -> 지도를 사용하려는 사람들이 원하는 기능에 비해 지도에 표시된 구조가 더 안정적이기 떄문이다.


지도로 은유하는 것에서 핵심
"기능"이 아니라 "구조"를 기반으로 모델을 구축하는 편이 좀 더 범용적이고 이해하기 쉬우며 변경에 안정적이라는 것이다.

### 표현적 차이

- 재언급, 소프트웨어 객체는 현실 객체 대한 추상화가 아니다.
- 소프트웨어 객체는 현실 객체를 모방하는 것이 아니라 은유를 기반으로 재창조하는 것이다.
	- 따라서, 소프트웨어 객체는 현실 객체가 갖지 못한 특성을 가질 수도 있고 현실 객체가 하지 못하는 행동을 할 수도 있다.
- 비록 소프트웨어 객체가 현실 객체를 왜곡한다고 하더라도 소프트웨어 객체는 현실 객체의 특성을 토대로 구축된다. 
	- 이처럼 소프트웨어 객체와 현실 객체 사이의 의미적 거리 == 표현적 차이 || 의미적 차이
	- 은유를 통해 현실 객체와 소프트웨어 객체 사이의 차이를 최대한 줄이는 것이다. ((생각) ??? 은유를 하면 거리가 멀어지는걸 허용하면서 만들어간다는거 아닌가? 왜지?)

- 기능적 요구사항 = 시스템이 사용자에게 제공해야하는 기능의 목록을 정리한 것

	- 사용자들이 시스템을 통해 달성하고자 하는 목표가 존재하기 때문이다.

### 유스케이스의 특성

1. 유스케이스는 사용자와 시스템 간의 상호작용을 보여주는 "텍스트"다.
	- (생각) 교수님들,,,
	- ![[Pasted image 20261128191302.png]]
2. 유스케이스는 하나의 시나리오가 아니라 여러 시나리오들이 집합이다.
3. 유스케이스는 단순한 피처 목록과 다르다.
4. 유스케이스는 사용자 인터페이스와 관련된 세부 정보를 포함하지 말아야 한다.
5. 유스케이스는 내부 설계와 관련된 정보를 포함하지 않는다.
6. "유스케이스는 설계 기법도, 객체지향 기법도 아니다."
